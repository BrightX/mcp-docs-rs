# 开发规范

本文件约束本项目的开发规则、代码质量要求与提交规范。所有贡献代码都应遵守。

## 1. 代码质量

- **简洁明了优先**：代码要能一眼看懂，不做炫技式写法。
- **避免过度设计**：三个相似的重复段落优于一个过早的抽象；只为当前需求设计，不为假想的未来需求铺路。
- **不引入不必要的抽象 / 配置 / 开关**：没有第二个使用者就不要抽 helper、加 feature flag、加兼容层。
- **不写防御性代码**：只在系统边界（用户输入、外部 API、文件内容）做校验，内部调用信任约定。
- **错误处理**：库内用 `thiserror` 定义错误类型，应用层用 `anyhow`；库代码禁止用 `unwrap` / `expect` / `panic!` 处理可预期错误（测试除外）。
- **不做无用注释**：注释解释「为什么」，不解释「是什么」（代码本身已表达）。

## 2. 代码风格

- 一律 `cargo fmt`（rustfmt 默认配置），不手工对抗格式化。
- `cargo clippy` 无警告（CI 用 `-D warnings`）。
- 命名遵循 Rust 惯例，标识符用英文（`snake_case` / `CamelCase`）。
- 提交前本地 `cargo test` 必须全绿。

## 3. 注释规范

- **统一使用简体中文**，包括模块文档 `//!`、条目文档 `///`、行内注释 `//`。
- 代码标识符、类型名、API 名称保持英文原样，不翻译。
- 文档注释（`///`）应说明：做什么、参数含义、返回值、可能的错误，必要时给示例。
- 只在该写的地方写：逻辑不自明处、非直觉的决策、外部约束的原因。
- 不保留被注释掉的死代码。

## 4. 提交规范

采用 Conventional Commits：`<type>: <描述>`

- type 用英文，描述用简体中文，一句话说清「做了什么」。
- 常用 type：

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `refactor` | 重构（不改变行为） |
| `test` | 测试 |
| `perf` | 性能 |
| `chore` | 杂项（构建、依赖、配置） |

- 示例：
  - `feat: 实现 sidebar-items.js 解析`
  - `fix: 修复 Windows 下文件名含冒号导致的写盘失败`
  - `docs: 补充 M2 里程碑验收标准`
- 提交要小而聚焦，一次提交只做一件事。
- 正文（可选）说明「为什么」，不复述 diff。

## 5. 工作流

- 每阶段（M0–M6）完成即更新 `docs/roadmap.md` 状态。
- 设计变更同步 `docs/design.md`；需求变更同步 `docs/requirements.md`。
- 正式文档一律放 `docs/`。

## 6. 文档管理

### 6.1 原则

- **单一事实来源**：每个事实只写一处，其他位置用链接引用，禁止复制粘贴。
- **只描述当前有效状态**：主文档不堆积历史，历史移入归档。
- **按主题拆，不按时间拆**（`lessons.md` / `glossary.md` 按章节）。

### 6.2 触发拆分的条件（满足其一即拆）

- 单文件 ≥ 400 行或 ≥ 30 KB；
- 一个文档里出现 ≥ 3 个可独立成篇的主题；
- `roadmap.md` 的已完成里程碑 ≥ 6 个。

### 6.3 拆分方式

文档改为同名目录，目录内 `README.md` 作导航，`docs/README.md` 索引同步更新：

| 原文档 | 拆分后 |
|---|---|
| `requirements.md` | `requirements/README.md` + `overview.md`（目标 / 约束 / 非目标）+ 按能力域（如 `core.md`、`cli.md`、`mcp.md`） |
| `design.md` | `design/README.md` + `facts.md`（实测事实底座，独立保留）+ `architecture.md` + `parsing.md` + `storage.md` + `mcp.md` + `testing.md` + `risks.md` |
| `roadmap.md` | `roadmap/README.md`（总览 + 进行中）+ `archive/`（已完成里程碑） |
| `lessons.md` / `glossary.md` | 单章节过大时才按章节拆文件（如 `lessons/1-parsing.md`），**编号 `#x.y` 保持不变** |

### 6.4 归档

- 已完成里程碑、被取代的设计决策 → `docs/archive/`，**保留不删除**，便于溯源；不参与日常维护。

### 6.5 编号稳定性

- `#x.y` 中 `x` 与主题绑定，拆分后不变（`#1.3` 永远属于主题 1）。
- 跨文档引用一律用相对链接。

### 6.6 兜底

- 若 `docs/` 整体膨胀到难以导航，可引入 mdBook 构建静态站点。当前不引入。
